# 第6章｜Proposal IR と出力レンダラ

前提：第5章は確定版として扱う。本章はその上に、出力形式を増やすための中間表現（Proposal IR）を定義する。

6-1. 目的と原則

・**Generator は AI を呼ばない。** IR の構築は、案件・ワークスペース・テンプレート・アセット・設定からの決定的な変換に限る。生成（AI呼び出し）は第4章のステップ実行が担い、その結果は provenance 付きでワークスペースに入っている。Generator はそれを組み替えるだけとする。
・**すべての出力形式は IR だけを入力にする。** Markdown・PDF・PowerPoint・Word のどれも、ワークスペースを直接読まない。形式を増やしても本文の組み立てロジックには触れない。
・**出力は追跡可能でなければならない。** 出た成果物が「どの生成ライン（Run）の、どの版（revision）から、どういう出自（provenance）で作られたか」を後から言えること。クライアントへ出す資料である以上、これは機能ではなく要件とする。

6-2. IR の構造

ProposalIR：
・irVersion：IRのスキーマ版。レンダラは対応外の版を拒否する。
・revision：内容から決定的に算出する版ID（6-3）。
・builtAt：構築時刻。revision の算出には含めない。
・lang：ja または en。言語ごとに別のIRを構築する。
・project：案件の識別情報（id、案件名、ブランド、クライアント、提案日、納期）。
・sections：章の並び。
・warnings：出力前に人が判断すべき事項（6-4）。
・sources：IR全体が参照した Run と provenance の要約。

Section：
・id、title
・blocks：本文ブロックの並び
・source：この章の出所（6-3）

Block（3種のみ。形式をまたいで表現できる最小構成とする）：
・paragraph：本文1段落
・list：箇条書き
・image：キャプション、アセット参照、出自、実体（data URI または外部URL）、フォールバック色

表・図はブロック種別を増やさず、現時点では list と paragraph で表現する。増やす場合は全レンダラの対応とセットで行う。

6-3. 出所の追跡（Run・revision・provenance）

Section.source：
・stepId：この章の内容を出力したステップ
・fields：参照したフィールドパス
・runIds：それらのフィールドを書いた生成ラインID（重複を除く）
・origins：フィールドごとの出自（generated／edited／empty）
・edited：1つでも手動編集済みのフィールドを含むか
・stale：ステップが stale か
・staleCause／staleAcknowledgedAt：stale の原因ステップと、確認済みの判断時刻

revision：
・IR から builtAt を除いた内容に対する決定的なハッシュ。同じ内容なら常に同じ revision になる。
・出力履歴（ExportRecord）に revision を残す。これにより「この PDF はどの版か」「その後に内容が変わったか」を照合できる。
・revision が同じなら、形式が違っても内容は同一であることを保証する。

6-4. 警告

IR は構築時に warnings を持つ。severity は warn（人の判断が要る）と info（知らせるだけ）。

・stale：上流の変更が反映されていない章がある（warn）
・acknowledged：stale を確認済みとして据え置いた章がある（info）
・missing-section：テンプレート上の章が未生成である（warn）
・missing-image：画像スロットにアセットが登録されていない（info）
・external-image：外部URL参照の画像がある。PDF／PowerPoint には埋め込まれない（info）

出力時：warn が1件でもあれば確認を挟む。ただし出力自体はブロックしない（第4章 4-4 と同じ方針）。出力物にも警告の要約を記載する。

6-5. レンダラ契約

・レンダラは `(ir, options) => Promise<RenderedFile>` の1関数。RenderedFile は fileName、mimeType、bytes（Uint8Array）を持つ。
・レンダラは IR 以外を読まない。ネットワークアクセスをしない。
・レンダラは IR を書き換えない。
・対応する irVersion を宣言し、一致しない IR は拒否する。

形式ごとの制約：

| 形式       | 実生成 | 日本語                                 | 画像                             |
| ---------- | ------ | -------------------------------------- | -------------------------------- |
| Markdown   | 対応   | 制約なし                               | 参照として記載                   |
| PDF        | 対応   | フォント埋め込みが必須                 | data URI の PNG／JPEG を埋め込む |
| PowerPoint | 対応   | フォント名参照（環境のフォントで描画） | data URI を埋め込む              |
| Word       | 未対応 | —                                      | —                                |

6-6. 日本語フォントと画像の扱い

PDF：
・PDF は指定された字形を自前で持つ必要があるため、日本語フォントの埋め込みが必須。埋め込まない PDF は環境によって文字が出ない。
・フォント（Noto Sans JP）はアプリのアセットとして持ち、PDF 出力時にのみ読み込む。初期表示には影響させない。
・使用文字だけを埋め込む（サブセット）。出力ファイルは小さく保つ。
・フォントが読み込めない場合は、文字化けした PDF を出さずにエラーとする。壊れた成果物を渡さないことを優先する。

PowerPoint：
・フォントは名前で参照する（日本語は Yu Gothic 系）。ファイルにフォントは含めない。開く環境のフォントで描画される。

画像：
・data URI（アップロード画像のサムネイル）は PDF・PowerPoint に埋め込む。
・外部URL参照の画像は、登録時に取り込めていれば埋め込む（6-8）。取り込めていない場合はキャプションと参照先だけを残し、警告（external-image）を出す。
・アセット未登録のスロットは、プレースホルダとして扱い、出力を壊さない。

6-7. 実装スコープ

・本章で実装するのは IR、revision、警告、Markdown／PDF／PowerPoint の3レンダラ、出力履歴への revision 記録まで。
・Word は未対応のまま残す。追加する場合もレンダラを1つ足すだけで済む構造にしてある。
・実モデル接続は本章の後。Generator が AI を呼ばないため、接続の有無は出力側に影響しない。

6-8. 外部URL画像の取り込み

・レンダラはネットワークを使わないため、実体を持たない外部URL画像は成果物に入らない。これはレンダラの決定性としては正しいが、画面に見えていた画像が成果物から消えるため、利用者からは不具合に見える。
・したがって**アセット登録の時点で取り込む**。URLを登録すると画像を取得し、上限に収まる形（必要なら縮小）でローカルに保持する。以降その画像は他のアセットと同じく埋め込まれる。
・取り込めない場合（CORS・ネットワーク・非画像・縮小できないほど大きい）は、**登録時にその理由を画面で明示する**。参照は残すが、成果物に含まれないことを登録直後とアセット表示の両方で示す。
・取り込みで保持するのは提案書プレビュー用の縮小版であり、原寸ではない。原寸の保存は次フェーズ（第7章）で扱う。
・**現状の実装は暫定である。** ブラウザからの直接フェッチは CORS で失敗するのが通常であり、成功するのは許可を出しているホストに限られる。したがって「取り込めない」が既定の結果になる前提で画面を作る：登録フォームではファイル登録を主動線とし、URL 欄には CORS 制限で取り込めないことが多い旨を**登録前に**示す。
・サーバー側プロキシ経由での取得を、API・サーバー永続化フェーズの要件に含める。プロキシが入るまで、URL 取り込みの成功率は環境依存のままとする。

6-9. 保存容量の枯渇（localStorage）

・画像は「保存失敗時はメモリ上で継続」をテキストと同じようには扱えない。テキストは再入力できるが、画像はリロードで消えると復元できないためである。したがって容量に関わる事象は必ず利用者に見せる。
・**上限**：サムネイル1枚96KB、合計2MB（base64 化を含む実効値）。localStorage の枠（約5MB）にはテキストと Run 履歴も同居するため、画像に割り当てるのは2MBまでとする。この上限では40枚弱で埋まり、ムードボード＋ショットリスト＋ポートフォリオを揃えると到達しうる。
・**可視化**：設定画面に使用量（使用KB／上限KB／使用率）と、保存済み枚数・参照のみ枚数を常時表示する。
・**上限接近時の警告**：使用率80%以上でアプリ全体に警告帯を出す。
・**超過時の明示的な拒否**：登録時に上限を超える場合は、サムネイルを黙って落とさず、理由（1枚の上限超過か、合計の枯渇か）を返して画面に出す。アセット自体は参照として登録し、「成果物に含まれません」と明示する。
・**保存時の失敗**：localStorage への書き込みが失敗した場合、サムネイルを退避して再試行し、退避したこと（degraded）または保存できていないこと（failed）を画面に出す。黙って継続しない。
・この節の上限は localStorage しか保存先が無いことに由来する暫定制約であり、**第7章で置き換え済み**。現在の画像の実体は IndexedDB にあり、localStorage に載るのはメタデータと variant の記述子だけである。したがって「サムネイルを退避して再試行する」経路は無くなり、保存失敗は failed としてそのまま画面に出る。容量の可視化・上限接近の警告は第7章 7-10、消失時の扱いは 7-11 に引き継いだ。
