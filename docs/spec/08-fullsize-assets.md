# 第7章｜原寸アセットの扱い

第5章のアセット仕様は52行で、保存先と解像度の要件を書かないまま実装に進んだ。その結果、サムネイル前提の制約がコードに埋まり、出力が提出物にならないという手戻りが出た。本章は同じことを繰り返さないため、実装前に保存先・参照解決・キャッシュ・印刷解像度・サムネイルと原寸の対応関係を書き切る。

7-1. 満たすべきこと

・提案書として提出できること。「PDF が出る」ではなく「PDF で提出できる」を到達点とする。
・画像はアプリ内で失われないこと。リロード・再訪で消えない。
・出力に使う画像と、画面に出す画像を区別すること。前者は原寸、後者は軽い派生物。
・解像度が足りない場合、出力前に分かること。出してから気づくのでは遅い。

7-2. 印刷解像度の要件

・提案書の版面は A4 縦（210×297mm）を基準とする。
・実寸配置での有効解像度は **200ppi を最低ライン、300ppi を目標**とする。200ppi を下回る画像は警告する。
・必要ピクセル数は「配置幅(mm) ÷ 25.4 × ppi」で求める。スロット別の目安は次のとおり。

| スロット             | 想定配置幅 | 200ppi 必要幅 | 300ppi 必要幅 |
| -------------------- | ---------- | ------------- | ------------- |
| 表紙キービジュアル   | 210mm 全面 | 1654px        | 2480px        |
| ムードボードのタイル | 62mm       | 488px         | 733px         |
| ブランドイメージ     | 100mm      | 787px         | 1181px        |
| 絵コンテのフレーム   | 62mm       | 488px         | 733px         |
| 実績（作品）         | 62mm       | 488px         | 733px         |

・現状のサムネイル（長辺約800px、96KB）は、タイル用途では 200ppi を満たすが、表紙全面では約 96ppi にしかならない。表紙に耐えないことが「提出できない」の実体である。

7-3. AI生成画像の解像度と印刷基準の乖離

原寸を保存できるようにしても、AI が生成した画像そのものが小さければ印刷基準には届かない。現行の画像生成モデルの出力は概ね長辺 1024〜2048px であり、A4 全面 300ppi（2480×3508px）を単独で満たすものは少ない。7-2 の必要幅に当てはめると次のようになる。

| 生成解像度（長辺） | 表紙 210mm | ブランドイメージ 100mm | タイル 62mm |
| ------------------ | ---------- | ---------------------- | ----------- |
| 1024px             | 124ppi     | 260ppi                 | 419ppi      |
| 1536px             | 186ppi     | 390ppi                 | 629ppi      |
| 2048px             | 248ppi     | 520ppi                 | 839ppi      |

・つまり **1K 級の生成画像はタイルには十分で、表紙全面には使えない**。2K でようやく表紙の最低ライン（200ppi）を超え、目標の 300ppi には届かない。制約はスロットごとに違うため、「AI画像は使える／使えない」ではなく「このスロットには足りない」と言える形にする。
・**実解像度はモデル定義側に持たせる。** 設定のモデル割り当て（第3章 3-13）に出力解像度を持たせ、実モデル接続フェーズで実測値を入れる。それまでは未確認として扱い、判定は生成後の実ピクセル数（variant の width／height）で行う。仕様がモデル名に依存しないようにするため、判定の入力は常に実測ピクセル数とする。
・**本章ではアップスケール処理を実装しない。** ブラウザ側の拡大（canvas 補間）は情報を増やさないため、必要ピクセル数の判定は通るが印刷品質は変わらない。警告だけが消えて問題が隠れるので、むしろ有害である。解像度を上げる手段は、生成モデル側の高解像度出力か、超解像 API の利用のどちらかであり、いずれも実モデル接続フェーズの範囲とする。
・**代わりにスロット単位で警告する。** 7-8 の `low-resolution` 警告は、スロット名・必要ピクセル数・実ピクセル数・換算 ppi を持つ。「表紙キービジュアルが 124ppi（必要 1654px に対し 1024px）」のように、どこをどう直せばよいかが分かる文言にする。
・**版面設計側の規約**：AI 生成アセットを表紙全面スロットへ既定で割り当てない。撮影実写または高解像度素材を優先し、AI 画像は既定でムードボードのタイルとブランドイメージに割り当てる。実装は次フェーズ（ビジュアル主導の版面設計）で行うが、規約は本章で決めておく。

7-4. 保存先

・**メタデータ**：これまでどおり localStorage。小さく、同期で読めることに価値がある。
・**バイナリ（原寸・派生物）**：**IndexedDB** に Blob として保存する。localStorage は文字列で約5MB が上限のため原寸を置けない。IndexedDB は Blob をそのまま保持でき、実用上は数百MB規模まで扱える。
・**判断の記録**：backlog では「サーバー側永続化の一部を前倒しする」としていた。前倒しするのは**アセットストアの契約（インターフェース）**であり、稼働するサーバーではない。契約を先に定義したうえで、当面の実装を IndexedDB に置く。理由は次の3点。
　・提出できる PDF を出すために必要なのは原寸の保持であって、共有ではない。共有はサーバーの価値であり、別の要件である。
　・サーバーを先に建てると、認証・権限・アップロード再開・保存期間といった論点が同時に来る。今必要な検証（原寸で出力できるか）はそれを待たずにできる。
　・契約を先に切っておけば、サーバー実装は同じ契約の別実装として差し替えられる。IndexedDB 実装は捨て石にならない。
・したがって本章では `AssetBinaryStore` を定義し、IndexedDB 実装を提供する。サーバー実装は第4フェーズ（API・サーバー永続化）で同じ契約に対して行う。

AssetBinaryStore（契約）：
・put(key, blob)：保存する。容量不足は例外ではなく結果として返す。
・get(key)：Blob を返す。無ければ undefined。
・delete(key)：削除する。
・usage()：使用量と、利用可能な見積もりを返す。
・list()：保持しているキーの一覧（孤児の掃除に使う）。

7-5. データモデル

Asset（第5章 5-1 を拡張）：
・id、origin、label、source、runId、mimeType、createdAt は据え置き。
・variants を追加する。

Variant：
・kind：original（原寸）または preview（画面表示用の派生物）
・key：AssetBinaryStore のキー
・width、height：ピクセル数。解像度判定に使う。
・bytes：保存サイズ
・mimeType

・原寸は 0 個または 1 個。preview は 0 個または 1 個。
・**参照は assetId のまま**とし、第5章 5-1 の参照解決（ムードボード・ショットリスト・ポートフォリオが assetId を持つ）は変更しない。variant の選択は用途側が行う。
・localStorage に残るのはメタデータと variant の記述子のみ。Blob は入れない。

7-6. サムネイルと原寸の対応関係

・**原寸が主、preview は派生物**とする。preview は原寸から決定的な規則で生成する：**長辺800px、JPEG 品質0.8**。生成規則を固定するのは、同じ原寸から同じ preview が得られるようにするため。
・登録時に原寸を保存し、続けて preview を生成して保存する。preview の生成に失敗しても原寸は残す（表示は原寸を縮小して行う）。
・原寸が無く preview だけがある状態（第6章までに登録された画像、または退避後）を許容する。この状態のアセットは**出力に使えない**ものとして扱い、画面と出力前警告で明示する。
・逆に preview が無く原寸だけの状態も許容する。表示が重くなるだけで、出力はできる。
・削除は原寸と preview を一括で行う。参照している側（タイル・カット・作品）からは assetId を外す。

preview を800pxとした理由と、3段構成を採らない理由：

・preview の用途は**画面表示だけ**であり、出力には使わない（出力は原寸のみ。preview しか無いアセットは警告付きで扱う）。画面上で最大の表示はアセットのプレビュー領域で、幅は 400px 程度。Retina を見込んで2倍でも 800px で足りる。1200px はどの表示にも使われない画素を運ぶことになる。
・**トレードオフ（3段構成＝thumbnail／preview／original の利点）**：一覧のタイルは表示幅 180px 程度で、そこに 800px の JPEG（1枚あたり概ね60〜100KB）を並べる。ムードボード12タイル＋ショットリストのサムネイルで 1〜2MB を復号して object URL に載せることになり、240px の thumbnail 段があればこれを1/10近くにできる。
・**3段構成の欠点**：variant の状態組み合わせが増え、「原寸あり／preview 欠損／thumbnail あり」のような部分欠損が3系統に増える。移行・削除・LRU・容量表示・用途側の variant 選択がすべて3系統になり、選択を1か所間違えると出力品質に直結する。第6章までの手戻り（サムネイルを出力に使ってしまった）と同型の事故を、より多い分岐で起こしうる。
・**判断：単段（original ＋ preview）で始める。** 現在のタイル数（ムードボード12、ショットリスト最大12、実績数点）であれば、800px 単段で実用上の問題は出ない見込みとする。**版面設計フェーズの後に実案件を1本通した時点で描画コストを実測**し、一覧の表示が問題になった場合に限り thumbnail 段を追加する。追加時の移行は原寸からの再生成で済むため、後戻りのコストは小さい（原寸が主であることの利点）。
・800px の preview は 62mm タイルでは 328ppi 相当になり、画面表示としては過剰なほど余裕がある。それでも**出力には使わない**。この一貫性を崩さないこと自体が本章の要件である。
・副次的な利点として、第6章までのサムネイル（長辺約800px、JPEG）と規格が一致するため、7-12 の移行は再生成なしに variant kind=preview へ読み替えるだけで済む。

7-7. 参照解決とキャッシュ

・メタデータの解決（resolveAsset）は**同期のまま**とする。IR の構築が同期であることは第6章の前提であり、崩さない。
・バイナリの取得は非同期とし、用途ごとに分ける。
　・画面：preview を取得し、object URL にして img に渡す。無ければ原寸から縮小表示する。
　・出力：原寸を取得する。無ければ preview を使い、警告を出す。
・**キャッシュ**：取得した Blob と object URL はメモリ上に LRU で保持する（既定16件）。object URL は LRU から落ちた時点で revoke する。revoke 漏れはメモリリークになるため、生成箇所を1つに閉じる。
・キャッシュはアプリ起動ごとに空から始める。IndexedDB 自体が永続層であり、二重の永続キャッシュは持たない。

7-8. IR と出力パイプラインの変更

第6章のレンダラ契約（IR 以外を読まない、ネットワークを使わない）は維持する。そのため、IR の構築と、バイナリの解決を**別のフェーズ**に分ける。

1. buildProposalIR（同期）：これまでどおり。image ブロックはバイナリを持たず、assetId・variant 記述子・出自・寸法だけを持つ。
2. resolveProposalAssets（非同期）：AssetBinaryStore から必要な variant を取得し、image ブロックに data を埋める。用途（画面／出力）で取る variant を変える。
3. renderer（IR のみ）：これまでどおり。渡された IR に data があれば埋め込み、無ければプレースホルダ。

・revision の算出には**バイナリを含めない**。含めると同じ内容でも解決の有無で版が変わってしまう。versionは「提案内容の版」であり、埋め込み実体の有無ではない。
・IR に警告 `low-resolution` を追加する（severity: warn）。スロットの想定配置幅（7-2）に対して必要ピクセル数を満たさない画像がある場合に出す。出力前の確認で表示し、出力物にも記載する。
・IR に警告 `preview-only` を追加する（severity: warn）。原寸が無く preview しか無い画像がある場合に出す。

7-9. revision と解決状態

解決（resolveProposalAssets）は非同期で、その結果は端末の保存状態に依存する。同じ内容の提案書でも、原寸が解決できた出力と preview へ落ちた出力が同じ revision を持ちうる。第6章 6-3 の「revision が同じなら内容は同一」という保証と衝突するため、扱いを決めておく。

・**revision には解決状態を含めない。** revision は「提案内容の版」であり、端末に原寸が残っているかどうかは内容ではない。含めると、同じ内容の提案書が端末や時点によって別の版に見え、6-3 の照合（この PDF はどの版か、その後に内容が変わったか）が成立しなくなる。
・したがって保証の文言を次のように精密化する。**「同じ内容 ⇒ 同じ revision」は維持する。「同じ revision ⇒ 同じファイル」は成立しない。** ファイルの同一性は revision と解決状態の**組**で判断する。
・**解決状態は出力履歴（ExportRecord）に別フィールドで持つ。** `assetResolution: { original: number; previewFallback: number; missing: number }` を記録し、どの出力が原寸で出たかを後から言えるようにする。履歴一覧では、previewFallback または missing が1件でもある出力に「一部が低解像度」と表示する。
・**ファイル名で区別する。** 原寸で解決できなかった画像を含む出力は、ファイル名に `-draft` を付ける（第6章 6-5 の命名に追加する）。同じ revision・同じ形式で中身の違うファイルが手元に同名で並ぶと、提出時に取り違える。提出物の事故防止を優先し、ここだけは名前を分ける。
・この規則は解決状態が変わったときの再出力を妨げない。原寸を再登録して出し直せば、内容が同じである限り revision は変わらず、`-draft` が外れた同じ版のファイルが得られる。これが期待される復旧手順である。

7-10. 容量と枯渇

・IndexedDB の容量はブラウザが動的に決めるため、固定の上限値は仕様に置かない。`usage()` が返す使用量と見積もり可能容量を画面に出す。
・保存失敗（QuotaExceededError）は第6章 6-9 と同じ方針で扱う：黙って落とさず、理由を画面に出し、原寸を保存できなかった場合は「出力に使えない」と明示する。
・削除導線を用意する。使用量の内訳（案件別・アセット別）を設定画面に出し、不要なものを解除できるようにする。

7-11. IndexedDB のデータ消失

第6章 6-9 は localStorage の**枯渇**（書けない）を仕様化したが、IndexedDB には別種の失敗がある。**一度書けたものが後から消える**。この非対称を放置しない。

・**性質**：IndexedDB の割り当ては端末の空き容量に依存し、固定の上限が無い。既定の保存は best-effort 扱いで、空き容量の逼迫時にオリジン単位で破棄されうる。とくに Safari は制約が強く、一定期間アクセスの無いサイトのスクリプト書き込みデータを破棄する。**放っておけば消えるものとして設計する。**
・**永続化の要求**：起動時に `navigator.storage.persist()` を呼び、`navigator.storage.persisted()` で現在の状態を読む。結果（granted／denied／未対応）を設定画面に常時表示する。granted 以外のときは「アプリを開かない期間が続くと画像が失われることがある」と明示し、重要な案件は出力して手元に保存するよう促す。API 非対応の環境は denied と同じ扱いにする（消えない保証が無い、が正しい表示）。
・**消失の検出**：メタデータは localStorage、バイナリは IndexedDB という分離のため、**両者の不一致が消失の観測点**になる。起動時に `list()` とメタデータの variant 記述子を突き合わせ、記述子はあるが実体が無いものを `missing` として記録する。使用中に `get()` が undefined を返した場合も同じく missing とする。
・**表示**：missing のアセットは画面上で「画像が失われています」と明示し、**再登録導線**（同じ assetId に原寸を貼り直す）を出す。参照している側（タイル・カット・作品）から assetId を**外さない**。外すと構成そのものが壊れ、貼り直すだけでは戻せなくなる。参照は保持したまま欠損状態で表示する。
・**出力を黙って劣化させない**：missing を含む状態での出力は、プレースホルダで静かに埋めない。IR に警告 `missing-binary`（severity: warn）を出し、出力前の確認で対象スロットと件数を示す。出力自体はブロックしない（第6章 6-4 の方針を維持する）が、成果物は 7-9 の規則により `-draft` 付きの名前になり、出力履歴にも missing 件数が残る。**「気づかないまま欠けた PDF をクライアントへ出す」経路を作らない**ことが本節の目的である。
・**共通の原則**：6-9（保存時に失敗する）と本節（保存後に消える）は検出の時点が違うだけで、扱いは同じ。理由を画面に出し、復旧の導線を示し、成果物への影響を明示する。黙って続行しない。

7-12. 移行

・localStorage のスキーマを v3 に上げる。
・既存の `Asset.thumbnail`（data URI）は、起動時に IndexedDB へ移し、variant kind=preview として記述子を残す。既存サムネイルは長辺約800px・JPEG で 7-6 の preview 規格と一致するため、再生成はしない。移行できたら thumbnail フィールドは落とす。
・移行に失敗した場合はメタデータのみを残し、preview-only として扱う（第6章までに登録した画像は原寸を持たないため、いずれにせよ出力には使えない）。
・移行はバージョンを見て一度だけ行い、結果を画面に出す。黙って消さない。

7-13. 実装スコープ

本章で実装する：
・AssetBinaryStore の契約と IndexedDB 実装
・Asset の variants 化と移行（v3）
・登録時の原寸保存と preview 生成（長辺800px／JPEG0.8）
・参照解決とキャッシュ（LRU、object URL の生存管理）
・resolveProposalAssets フェーズと、PDF／PowerPoint での原寸埋め込み
・low-resolution／preview-only／missing-binary 警告と、容量の可視化・削除導線
・永続化の要求（`navigator.storage.persist()`）、消失の検出と再登録導線
・出力履歴の解決状態（assetResolution）と `-draft` 命名

本章では実装しない：
・アップスケール（生成モデル側または超解像 API の話であり、実モデル接続フェーズ。理由は 7-3）
・thumbnail 段の追加（実案件の通し検証で描画コストを実測してから判断する。理由は 7-6）
・サーバー実装（同じ契約の別実装として第4フェーズで行う）
・外部URL取得のプロキシ（同上）
・版面設計（次フェーズ「ビジュアル主導の版面設計」）
