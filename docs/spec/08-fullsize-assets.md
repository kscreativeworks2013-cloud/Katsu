# 第7章｜原寸アセットの扱い

第5章のアセット仕様は52行で、保存先と解像度の要件を書かないまま実装に進んだ。その結果、サムネイル前提の制約がコードに埋まり、出力が提出物にならないという手戻りが出た。本章は同じことを繰り返さないため、実装前に保存先・参照解決・キャッシュ・印刷解像度・サムネイルと原寸の対応関係を書き切る。

7-1. 満たすべきこと

・提案書として提出できること。「PDF が出る」ではなく「PDF で提出できる」を到達点とする。
・画像はアプリ内で失われないこと。リロード・再訪で消えない。
・出力に使う画像と、画面に出す画像を区別すること。前者は原寸、後者は軽い派生物。
・解像度が足りない場合、出力前に分かること。出してから気づくのでは遅い。

7-2. 印刷解像度の要件

・提案書の版面は A4 縦（210×297mm）を基準とする。
・実寸配置での有効解像度は **200ppi を最低ライン、300ppi を目標**とする。200ppi を下回る画像は警告する。
・必要ピクセル数は「配置幅(mm) ÷ 25.4 × ppi」で求める。スロット別の目安は次のとおり。

| スロット             | 想定配置幅 | 200ppi 必要幅 | 300ppi 必要幅 |
| -------------------- | ---------- | ------------- | ------------- |
| 表紙キービジュアル   | 210mm 全面 | 1654px        | 2480px        |
| ムードボードのタイル | 62mm       | 488px         | 733px         |
| ブランドイメージ     | 100mm      | 787px         | 1181px        |
| 絵コンテのフレーム   | 62mm       | 488px         | 733px         |
| 実績（作品）         | 62mm       | 488px         | 733px         |

・現状のサムネイル（長辺約800px、96KB）は、タイル用途では 200ppi を満たすが、表紙全面では約 96ppi にしかならない。表紙に耐えないことが「提出できない」の実体である。

7-3. 保存先

・**メタデータ**：これまでどおり localStorage。小さく、同期で読めることに価値がある。
・**バイナリ（原寸・派生物）**：**IndexedDB** に Blob として保存する。localStorage は文字列で約5MB が上限のため原寸を置けない。IndexedDB は Blob をそのまま保持でき、実用上は数百MB規模まで扱える。
・**判断の記録**：backlog では「サーバー側永続化の一部を前倒しする」としていた。前倒しするのは**アセットストアの契約（インターフェース）**であり、稼働するサーバーではない。契約を先に定義したうえで、当面の実装を IndexedDB に置く。理由は次の3点。
　・提出できる PDF を出すために必要なのは原寸の保持であって、共有ではない。共有はサーバーの価値であり、別の要件である。
　・サーバーを先に建てると、認証・権限・アップロード再開・保存期間といった論点が同時に来る。今必要な検証（原寸で出力できるか）はそれを待たずにできる。
　・契約を先に切っておけば、サーバー実装は同じ契約の別実装として差し替えられる。IndexedDB 実装は捨て石にならない。
・したがって本章では `AssetBinaryStore` を定義し、IndexedDB 実装を提供する。サーバー実装は第4フェーズ（API・サーバー永続化）で同じ契約に対して行う。

AssetBinaryStore（契約）：
・put(key, blob)：保存する。容量不足は例外ではなく結果として返す。
・get(key)：Blob を返す。無ければ undefined。
・delete(key)：削除する。
・usage()：使用量と、利用可能な見積もりを返す。
・list()：保持しているキーの一覧（孤児の掃除に使う）。

7-4. データモデル

Asset（第5章 5-1 を拡張）：
・id、origin、label、source、runId、mimeType、createdAt は据え置き。
・variants を追加する。

Variant：
・kind：original（原寸）または preview（画面表示用の派生物）
・key：AssetBinaryStore のキー
・width、height：ピクセル数。解像度判定に使う。
・bytes：保存サイズ
・mimeType

・原寸は 0 個または 1 個。preview は 0 個または 1 個。
・**参照は assetId のまま**とし、第5章 5-1 の参照解決（ムードボード・ショットリスト・ポートフォリオが assetId を持つ）は変更しない。variant の選択は用途側が行う。
・localStorage に残るのはメタデータと variant の記述子のみ。Blob は入れない。

7-5. サムネイルと原寸の対応関係

・**原寸が主、preview は派生物**とする。preview は原寸から決定的な規則で生成する：長辺1200px、JPEG 品質0.8。生成規則を固定するのは、同じ原寸から同じ preview が得られるようにするため。
・登録時に原寸を保存し、続けて preview を生成して保存する。preview の生成に失敗しても原寸は残す（表示は原寸を縮小して行う）。
・原寸が無く preview だけがある状態（第6章までに登録された画像、または退避後）を許容する。この状態のアセットは**出力に使えない**ものとして扱い、画面と出力前警告で明示する。
・逆に preview が無く原寸だけの状態も許容する。表示が重くなるだけで、出力はできる。
・削除は原寸と preview を一括で行う。参照している側（タイル・カット・作品）からは assetId を外す。

7-6. 参照解決とキャッシュ

・メタデータの解決（resolveAsset）は**同期のまま**とする。IR の構築が同期であることは第6章の前提であり、崩さない。
・バイナリの取得は非同期とし、用途ごとに分ける。
　・画面：preview を取得し、object URL にして img に渡す。無ければ原寸から縮小表示する。
　・出力：原寸を取得する。無ければ preview を使い、警告を出す。
・**キャッシュ**：取得した Blob と object URL はメモリ上に LRU で保持する（既定16件）。object URL は LRU から落ちた時点で revoke する。revoke 漏れはメモリリークになるため、生成箇所を1つに閉じる。
・キャッシュはアプリ起動ごとに空から始める。IndexedDB 自体が永続層であり、二重の永続キャッシュは持たない。

7-7. IR と出力パイプラインの変更

第6章のレンダラ契約（IR 以外を読まない、ネットワークを使わない）は維持する。そのため、IR の構築と、バイナリの解決を**別のフェーズ**に分ける。

1. buildProposalIR（同期）：これまでどおり。image ブロックはバイナリを持たず、assetId・variant 記述子・出自・寸法だけを持つ。
2. resolveProposalAssets（非同期）：AssetBinaryStore から必要な variant を取得し、image ブロックに data を埋める。用途（画面／出力）で取る variant を変える。
3. renderer（IR のみ）：これまでどおり。渡された IR に data があれば埋め込み、無ければプレースホルダ。

・revision の算出には**バイナリを含めない**。含めると同じ内容でも解決の有無で版が変わってしまう。versionは「提案内容の版」であり、埋め込み実体の有無ではない。
・IR に警告 `low-resolution` を追加する（severity: warn）。スロットの想定配置幅（7-2）に対して必要ピクセル数を満たさない画像がある場合に出す。出力前の確認で表示し、出力物にも記載する。
・IR に警告 `preview-only` を追加する（severity: warn）。原寸が無く preview しか無い画像がある場合に出す。

7-8. 容量と枯渇

・IndexedDB の容量はブラウザが動的に決めるため、固定の上限値は仕様に置かない。`usage()` が返す使用量と見積もり可能容量を画面に出す。
・保存失敗（QuotaExceededError）は第6章 6-9 と同じ方針で扱う：黙って落とさず、理由を画面に出し、原寸を保存できなかった場合は「出力に使えない」と明示する。
・削除導線を用意する。使用量の内訳（案件別・アセット別）を設定画面に出し、不要なものを解除できるようにする。

7-9. 移行

・localStorage のスキーマを v3 に上げる。
・既存の `Asset.thumbnail`（data URI）は、起動時に IndexedDB へ移し、variant kind=preview として記述子を残す。移行できたら thumbnail フィールドは落とす。
・移行に失敗した場合はメタデータのみを残し、preview-only として扱う（第6章までに登録した画像は原寸を持たないため、いずれにせよ出力には使えない）。
・移行はバージョンを見て一度だけ行い、結果を画面に出す。黙って消さない。

7-10. 実装スコープ

本章で実装する：
・AssetBinaryStore の契約と IndexedDB 実装
・Asset の variants 化と移行（v3）
・登録時の原寸保存と preview 生成
・参照解決とキャッシュ（LRU、object URL の生存管理）
・resolveProposalAssets フェーズと、PDF／PowerPoint での原寸埋め込み
・low-resolution／preview-only 警告と、容量の可視化・削除導線

本章では実装しない：
・サーバー実装（同じ契約の別実装として第4フェーズで行う）
・外部URL取得のプロキシ（同上）
・版面設計（第3フェーズ「ビジュアル主導の版面設計」）
