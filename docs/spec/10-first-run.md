## 9-2. e2e が10件のまま変わっていない理由

単体テストは 167→180（+13）、e2e は 10 のまま（`assets.spec.ts` 6／`smoke.spec.ts` 4）。

理由は、直近の変更をすべて**ドメイン層と PDF 出力**で検証したためである。配置幅・面付け・禁則・色の導出・キャプション・提出前チェックは、いずれもブラウザを起動せずに PDF のバイト列まで検証できる（`placement.test.ts` は実際に PDF のクリップ矩形を読んでいる）。ここに e2e を足しても、遅くなるだけで新しいことは分からない。

**ただし画面を伴う変更が2つあり、そちらは穴が空いている。** 指摘のとおりである。

| 変更                              | ドメイン層        | 画面の単体テスト | e2e      |
| --------------------------------- | ----------------- | ---------------- | -------- |
| 枠の選択（`SlotPicker`）          | picks.test.ts 3本 | **無し**         | **無し** |
| 切り出し位置（`CropFocusPicker`） | 版面側で検証      | **無し**         | **無し** |

穴の具体的な中身：

・チェックボックスの操作が `setSlotPicks` を正しい `slotId` で呼ぶか。
・選択が `Workspace.picks` に入り、リロード後も残るか（localStorage 経路）。
・選択した順で PDF に載るか（ドメインでは検証済み、画面からの結線は未検証）。
・「既定に戻す」で `picks` から該当キーが消えるか。
・枠数以下の供給元で `SlotPicker` が出ないこと。
・切り出し位置の10択が `Workspace.crops` に入り、PDF の切り出しに反映されるか。

実案件1本を手作業で通す過程でこの経路は必ず通るので、通した後に e2e を書く（通しの前に書くと、通しで仕様が動いたときに書き直しになる）。

## 9-3. PDF の実サイズとフォント軽量化

### 実測（現在・HEAD b9ea873）

`dist/layout-preview/adopted.pdf`（11面・日本語版）

| 内訳                           | バイト                   | 割合      |
| ------------------------------ | ------------------------ | --------- |
| ファイル全体                   | 10,446,995（9.96 MB）    | 100%      |
| 画像ストリーム                 | 7,197,740（6.86 MB）     | 68.9%     |
| **フォント（1本・Flate 後）**  | **3,155,324（3.01 MB）** | **30.2%** |
| その他（内容ストリーム・構造） | 約 90 KB                 | 0.9%      |

`grid-6x6.pdf`（10面）は 8,387,209 バイト。うち画像 5,139,910、フォントは同じ 3,155,324。

英語版は未計測だが、レンダラは**日英どちらでも和文フォントを無条件に埋め込む**（pdfLayout.ts:503）。英語版でも見出しの一部に和文が残るため単純には外せない。よって日英2本を出せば同じ 3.01 MB を2回運ぶ。

### 軽量化の見通し（実測）

`pyftsubset`（fontTools 4.63.0、この環境に導入済み）で Noto Sans JP 400Regular を JIS X 0208（第1・第2水準＋かな＋記号）＋欧文・記号の補いへ絞った結果：

|                | 生バイト             | Flate 後                  | 収録グリフ |
| -------------- | -------------------- | ------------------------- | ---------- |
| 現行（全字形） | 5,472,784（5.22 MB） | 3,155,324（3.01 MB）      | 全数       |
| 絞り込み後     | 2,264,416（2.16 MB） | 1,342,177 相当（1.28 MB） | 7,560      |

**フォントは 3.01 MB → 1.28 MB（−1.73 MB）。PDF 全体では 9.96 MB → 8.23 MB。**

### 目標「1本1MB前後」への到達可否

**フォント軽量化だけでは届かない。** 支配項は画像で 6.86 MB あり、フォントを 0 にしても 6.9 MB 残る。原因は、印刷を前提に**原寸（original）をそのまま埋めている**ためで、これは第7章の設計どおりである。

1MB 前後を狙うなら、フォントとは別に出力の系統を分ける必要がある。

・**印刷用**：原寸・全字形（または絞り込み後）埋め込み。現行のまま。10 MB 前後。
・**送付用**：長辺 2000px 程度へ再エンコードした画像＋絞り込みフォント。画像が 1.5 MB 前後まで落ちるので、合計 2〜3 MB。1 MB は 11 面・画像 15 点では厳しい。
・画像を preview 段（長辺 1600px）まで落とせば 1 MB 台に入るが、**印刷に耐えない PDF を出せる導線を作ることになる**ため、命名（`-draft` 相当）と警告をどう出すかを先に決める必要がある。

判断を仰ぐ点：フォント軽量化（−1.73 MB、副作用ほぼ無し）は実施してよいか。「送付用」出力の新設まで踏み込むかは、実案件1本で実際の面数・画像点数を見てから決めたい。

### 字形集合の事前確認（指示どおり先に実施）

ソース全体（`src/`・`docs/spec/`・`tools/` の .ts/.tsx/.md、108 ファイル）に現れる文字 1,121 種を JIS X 0208 と突き合わせた。**JIS 外は 40 種**。

```
¥ À È É Ō Œ œ Š š Ÿ Ž ž ƒ ɏ ˆ ˜ – — ‚ „ • ‹ › ‼ ⁉ € ℉ ™ ⇄ ✓ 〖 〗 〘 〙 ゕ ゖ 䄀 䄄 䈀 ～
```

内訳と扱い：

・`Ō Œ œ Š š Ÿ Ž ž À È É`：ブランド名・人名の欧文（`KŌHAKU` 等）。**必須**。Latin-1 Supplement と Latin Extended-A を追加して収録した。
・`– — ‚ „ • ‹ ›`：欧文の約物。英語版の本文で使う。**必須**。General Punctuation を追加。
・`€ ™ ℉ ¥ ✓ ⇄ ‼ ⁉`：通貨・記号。**必須**。通貨記号・Letterlike・矢印・記号ブロックを追加。
・`〖〗〘〙 ゕ ゖ`：仕様書の記述で使った括弧と小書きかな。CJK 記号・かなブロックに含めて収録。
・`ƒ ɏ ˆ ˜ 䄀 䄄 䈀`：テストに埋め込んだ base64 の断片が文字として読まれたもの。**本文には出ない**。

上記を足した集合（8,281 符号位置）でサブセットを作り、`漆黒帛琥珀撮影提案書美容化粧品魅了` を含む抽出検査で欠落が無いことを確認した。**実案件の本文に固有名詞の異体字（髙・﨑など）が出た場合は JIS 外になりうる**ので、通しの過程で実際の本文を突き合わせる（9-6 の計測項目に含める）。

なお、実行時のサブセット化は引き続き行わない。pdf-lib のサブセット書き出しは壊れた `glyf` を吐き、出力側から検知できない（実測：47 字中 38 字の輪郭が欠落）。**ビルド時に絞り、実行時は絞らない**という方針は変えない。

## 9-5. (B) 日英の通し方（決定待ち）

海外レップ提出が最終目的である以上、英語版込みで通すと「日本語だけ編集した章が英語版ごと保護され、再生成しても英語版が古いまま固定される」経路に即座に当たる。章本文が日英を同一フィールドに持ち、provenance がフィールド単位だからである。

### 案A：1本目は日本語のみ。日英 provenance の分離はフェーズ3のまま

・利点：通しが最短で終わる。版面・原寸・手動編集・提出前チェックという第8章までの成果を、余計な変数なしに評価できる。フェーズの順序（実案件→実モデル→サーバー）を崩さない。
・欠点：英語版の版面が未検証のまま残る。英文は同じ内容でも行数が増えるので、**版面が破綻する閾値は英語のほうが低い可能性が高い**。1本目の計測結果が日本語だけの数字になる。

### 案B：日英 provenance の分離を通しの前へ前倒しし、両方で通す

・利点：最終目的（海外提出）の形で1本目を評価できる。英文の分量で版面が破綻するかを最初から見られる。
・欠点：分離は `SectionContent` のフィールド設計とカスケード規則に触るため小さくない。通しの着手が遅れ、通しで得たかったこと（版面が実分量に耐えるか）の答えが後ろへずれる。

### 提案：**案A′**（案Aの変形）

1本目は**日本語で本文を書き、英語版は生成させて出力だけ確認する（編集しない）**。

・日英 provenance の問題は「日本語だけ**編集**した章」で起きる。編集を日本語側だけに閉じ、英語版は生成のままにしておけば、1本目の間はこの経路に入らない。
・それでいて**英語版の PDF は出る**ので、英文の分量で版面が破綻するか、フォントとファイルサイズが日英でどう違うかは計測できる（9-3 で未計測としたところが埋まる）。
・通しの結果として「英語版の版面が持たない」と分かれば、provenance の分離より版面の修正が先だと判明する。逆に持つなら、分離は予定どおりフェーズ3でよい。
・**1本目の成果物をそのままレップへ出すことはできない**（英語版を手で直せないため）。これが案A′の代償で、それを許容できるかが判断の分かれ目になる。

判断は指示を待つ。案Bを採る場合、分離の見積もりを先に出す。

## 9-7. PowerPoint 16:9 の先行検証（通しと同時）

表紙かムードボードのいずれか**1面だけ**を 16:9 へ流し、版面定義が相対座標として機能しているかを確かめる。

理由：ここが崩れているとフェーズ4（PowerPoint の面付け）が丸ごと作り直しになる。全面を作ってから気づくより、1面で先に確かめるほうが安い。

見るところ：

・`SCREEN_16_9` を渡したとき、安全マージン・見出し位置・タイル格子が比率のまま追随するか。
・`cellSize()` の縦横比上限（`MAX_CELL_ASPECT`）が 16:9 で効きすぎて枠が痩せないか（A4横より横長なので、幅の上限より高さの上限が先に当たる可能性がある）。

## 9-10. 工程00-a：状態の書き出しと読み込み

### なぜ通しの前提なのか

11章ぶんの本文を実物の分量で手入力すると、**数時間の作業が localStorage と IndexedDB だけに載る**。どちらもブラウザの都合で消えうる。v2→v3 の移行でシードへ戻った実績があり、永続化が `denied` の端末では放置しただけで破棄される。第7章 7-11 の消失検出と貼り直しは「画像の実体が消えたとき」の復旧であって、**案件データそのものが消えたときの出口は無かった**。ここを塞がずに通しへ入ると、事故ったときに作業が全部消える。

### 形式

`kind: 'lbvpos.backup'` を持つ JSON 1ファイル。中身は書き出し形式の版（`BACKUP_VERSION`）と、状態そのもの（`PersistedState` ＝ 案件・ワークスペース・provenance・Run履歴・アセットのメタデータ・実績・設定）と、画像の実体の配列。

### 画像の実体を含めるか（提案と採用）

**両方を用意し、含める側を既定にした。**

・**画像を含めて書き出す**（既定）：AssetBinaryStore の実体を全件 data URI にして同じ JSON へ入れる。1ファイルで完全に戻る。原寸ぶん大きくなる（実素材15点で 10MB 前後）。
・**メタデータだけ書き出す**：小さい。ただし**復元後は原寸の貼り直しが要る**。画面にもその旨を出す。復元直後は記述子だけが残るので、既存の消失検出（第7章 7-11）がそのまま拾い、貼り直し導線に乗る。新しい経路を足していない。

含める側を既定にした理由は、メタデータのみの復元が「利用者の手元に元のファイルがまだある」ことを前提にするからで、それは事故の状況でいちばん当てにならない前提である。

### 版が違うとき

**黙って読まない。** 読めなければ理由を出して拒否し、状態には一切触れない。

| 状況                             | 挙動                                                 |
| -------------------------------- | ---------------------------------------------------- |
| 種別が違う（他所の JSON）        | 拒否。「このアプリの書き出しファイルではありません」 |
| 書き出し形式が新しい             | 拒否。「アプリを更新してから読み込んでください」     |
| 状態の形式が新しい               | 拒否。読める版を明示する                             |
| 状態の形式が古く、移行が定義済み | 移行して読む（`STATE_MIGRATIONS` を順に適用）        |
| 状態の形式が古く、移行が未定義   | 拒否。「読み込むと内容が壊れるため中止しました」     |
| 画像データの一部が壊れている     | 拒否（部分的に読まない）                             |

保存側の `loadState()` は版違いを `null` にして落とすが、それは「保存済みの状態が古い」場合の話である。**利用者が明示的に指定したファイルを黙って捨ててよい理由にはならない**ので、こちらは必ず理由を返す。

`STATE_MIGRATIONS` はいま空でよい（書き出しは v3 の状態からしか作られない）。v4 を作るときは `3: (v3) => v4` の向きで足す。

### 復元の順序

実体を先に入れ、そのあとメタデータを差し替える。逆にすると、途中で失敗したときに「記述子はあるのに実体が無い」＝消失として見えてしまう。

復元は**置き換え**であって併合ではない。同じIDの案件が両方にあるとき、どちらを採るかを機械が決めると取り返しがつかないため、判断は利用者に残す（画面にも明記する）。

### 検証

・単体10本（`src/domain/backup.test.ts`）。往復・種別違い・壊れた JSON・版の上下・案件データ無し・画像データ破損。
・e2e 2本（`e2e/backup.spec.ts`）。**画像を登録 → 書き出し → localStorage と IndexedDB を両方削除 → リロード（原寸あり 0件を確認）→ ファイルから読み込み → 原寸あり 1件に戻り、実績の画像が再び表示される**。もう1本は他所の JSON を読ませて、拒否されること・状態が変わらないことを見る。

ダウンロード・IndexedDB・canvas は jsdom に無いため、ここは実ブラウザでしか通せない。

## 9-13. 工程00-b：フォント軽量化・欠字検出・英語版の条件付き埋め込み

### (1) 絞り込み

`tools/fonts/subset.py` が `pyftsubset` で軽量版を作り、`src/assets/fonts/NotoSansJP-jis.ttf` に置く（`npm run fonts:subset`）。**実行時には絞らない**——pdf-lib の実行時サブセット化は壊れた `glyf` を吐き、出力側から検知できない（実測：47字中38字の輪郭が欠落）。

ビルド時に生成せずリポジトリへ置く理由は、生成に Python と fontTools が要り、それをビルドの必須条件にしたくないため。字形集合を変えたら再生成して生成物ごとコミットする。

### (2) 収録する字形集合と、水準の選び方

JIS X 0208（第1・第2水準）を基礎に、欧文・約物・通貨・矢印・**丸数字**（U+2460–24FF）・**単位記号**（U+3200–33FF の ㎡ ㎜ ㈱）・**互換漢字**（U+F900–FAFF、﨑 などの人名異体字）・半角全角を足す。JIS X 0208 にも上の範囲にも入らない人名の字（髙 德 濵 嶋 曾 邊 邉 栁 𠮷）は個別に追加した。

**JIS X 0213（第3・第4水準）まで広げる案は実測で退けた。**

| 集合                           | 指定符号位置 | 生バイト    | Flate 後    |
| ------------------------------ | ------------ | ----------- | ----------- |
| 絞らない（現行）               | 全数         | 5.22 MB     | 3.01 MB     |
| **JIS X 0208 ＋ 追加（採用）** | **10,028**   | **2.40 MB** | **1.39 MB** |
| JIS X 0213 ＋ 追加             | 16,881       | 4.63 MB     | 2.68 MB     |
| CJK統合漢字を丸ごと            | 31,104       | 4.52 MB     | 2.61 MB     |

第3・第4水準まで入れると削減が 1.62MB → 0.33MB になり、軽量化の意味が消える。**足りない字は出力時に検知して列挙する**ので、黙って落ちることはない。

### 欠字の検知

`src/domain/render/fontCoverage.ts`。1面も描く前に、紙へ乗る文字列すべてと**実際に埋め込むフォントの cmap** を突き合わせ、字形が無ければ該当文字を符号位置つきで列挙して例外にする。「フォントを読み込めなければ PDF を出さない」（第6章 6-6）と同じ扱い。

宣言した範囲ではなく**実物の cmap** を見るので、`subset.py` の集合とフォントの中身がずれても検知は正しいままになる。

突き合わせの対象は3つ。どれか1つでも漏らすと読み違える。

1. IR のテキスト（章題・本文・箇条書き・キャプション・マップのラベル・警告文・枠名）。画像の実体（data URI）は描かれないので入れない。
2. **版面が持つ文字**（出自ラベル・箇条書き記号・表紙の日付行・注意書きの見出し）。
3. **注意書きと提出前チェックの文**。これはレンダラ側で組み立てるので IR に載っていない。

和文側に回る文字の判定は描画と同じ `splitRuns` に任せる。ここで別の判定を書くと「欧文フォントで描かれるのに和文フォントの収録を問う」ずれが出る。

### (3) 英語版の条件付き埋め込み

和文フォントを1文字も使わない面付けでは埋め込まない。判定は IR から決まるので、同じ IR からは必ず同じファイルが出る。

要件は「CJK が1文字も無ければ」だが、実装は**欧文フォントで描けるか**で判定する。`KŌHAKU` の `Ō` は CJK ではないが標準14書体では符号化できず和文フォントへ回るため、CJK の有無で判定すると字が消える。純粋な英文では結果は同じで、安全な側に倒れる。

**この過程で、版面が持つ文字がすべて和文だったことが分かった。** 出自ラベル・箇条書きの `・`・`提案日 …／版 …`・`（提案位置）`・注意書きの見出しがそれで、`／` 1文字のために 1.39MB を運ぶ形になっていた。`CHROME` を `ir.lang` で引き分けるようにした。

### 実測（HEAD 時点・11面／画像15点）

|                          | 全体                 | 画像    | フォント                 | その他 |
| ------------------------ | -------------------- | ------- | ------------------------ | ------ |
| `adopted.pdf`（日本語）  | 8,714,844（8.31 MB） | 6.86 MB | **1,459,388（1.39 MB）** | 38 KB  |
| `adopted-en.pdf`（英語） | 8,714,767（8.31 MB） | 6.86 MB | **1,459,388（1.39 MB）** | 38 KB  |
| `grid-6x6.pdf`           | 6,655,070（6.35 MB） | 4.90 MB | 1,459,388                | 38 KB  |

**フォントは 3.01 MB → 1.39 MB。1本あたり 1.62 MB 減り、PDF は 9.96 MB → 8.31 MB。** テキスト層は無傷（本文・数字・記号を PDF から読み出して確認）。

### 英語版でフォントが落ちなかった理由（報告）

条件付き埋め込みは実装したが、**現在の英語版では発火しない**。和文が2か所残るため。

1. **提出前チェックと出力時の注意が、`ir.lang` によらず和文で組まれる。** 実際の出力：`Pre-submission checklist / - Selected Worksは6件中3件のみ掲載されます（「選定作品」の枠）。` 見出しだけ英語になり、中身が和文。
2. **英語版の本文そのものに和文が残る。** モック生成が英訳しない値をそのまま置いている（`Hair & make-up: ナチュラル／艶感重視`、`Location: 都内スタジオ（自然光）＋ロケ1日`）。

1 はレンダラ側（`domain/render/types.ts` の `warningSummary`／`checklistSummary`）を言語で引き分ければ解ける。2 は生成側の話で、実モデル接続（フェーズ1）か日英分離（9-12）の範囲。**どちらも解ければ英語版は 1.39 MB 軽くなる**が、いま手を付けると通しの前に範囲が広がるので backlog へ送る。

### 目標「1本1MB前後」について

**届いていない。** 8.31 MB のうち 6.86 MB が画像で、フォントを 0 にしても 6.9 MB 残る。原寸をそのまま埋めているためで、これは第7章の設計どおり。1MB 台に入れるには画像を再エンコードする「送付用」の出力系統が要るが、印刷に耐えない PDF を出せる導線を作ることになるので、命名と警告の扱いを含めて**通しの後に判断する**。

## 9-14. 工程00-b-1：コミット済みフォントと生成スクリプトの一致

## 9-16. 工程00-c：重複検知に実績を加える

### 対象の枠

`PROMINENT_SLOTS` に `works-grid` を足した。**`shot-frames` は残した**——外すと前回指示（ショットリストを対象に含める）を取り消すことになる。現在の対象は5枠。

| -------------------------------- | ------------------ |
| `cover-key` 表紙のキービジュアル | ムードボード       |
| `brand-mood` ブランド分析        | ムードボード       |
| `concept-key` 撮影コンセプト     | ムードボード       |
| `shot-frames` ショットリスト     | 絵コンテ           |
| **`works-grid` 実績**            | **ポートフォリオ** |

### ムードボードの除外は、どこまで有効か

ムードボードを対象に入れないのは「**素材の一覧そのもの**であり、選んだ1枚がそこにも並ぶのは参照元の提示だから」である。この理屈が成り立つのは**ムードボードから引いている枠**（表紙・ブランド分析・撮影コンセプト）に対してだけで、供給元の違う枠には成り立たない。

**実績に対しては成り立たない。** 実績は「自分の仕事」であって参照元ではないので、ムードボードと同じ写真が出るなら、参考画像を自作として見せていることになる。ショットリスト（供給元は絵コンテ）も同じ。

### 別IDで中身が同じ場合

同じ写真をムードボードと実績に別々に登録すると**アセットIDは別になる**（実測：`06-mood-ring.jpg` と `12-work-ring.jpg` は SHA-256 が一致するが別ID）。IDの一致だけでは気づけないので、実体の**寸法とバイト数**を指紋にして照合する。IR に `IRImageVariant.bytes` を足した（IR は保存しないのでスキーマ版には影響しない）。

ただし指紋の照合は**供給元をまたぐ場合に限る**。同じ供給元の中で寸法とバイト数がたまたま揃った別々の写真——生成画像のように寸法が揃いやすい素材で起こる——を重複として出すと、正常な構成で常時警告になる。供給元が同じなら、本当に同じアセットである限りIDの一致が拾う。

### 出力での確認

`adopted.pdf` の提出前チェックに次の行が出るようになった。

```
・同じ画像が2か所に使われています：ムードボード／手元のクローズアップ、実績／Bare Pigment。
```

severity は `info`。出力を壊すわけではないが、提出前に気づける必要がある。

### R-4｜容量の数字

**どちらの数字も、警告も登録拒否も駆動していなかった。**

・**80%警告は存在しなかった。** 閾値はコードのどこにも無い。
・**登録拒否は数字を見ていない。** `store.put()` が IndexedDB に書き込み、ブラウザが `QuotaExceededError` を投げたときだけ拒否する。事前判定は無い。
・したがって「quota 1.1GB / usage 597KB では警告が永久に発火しない」はご指摘のとおりだが、実態は**発火する警告そのものが無かった**。
・`estimate().usage` は `indexedDbStore` が取得しているが `assetUsage` へ渡っておらず、**どこにも表示されていない**。画面の「6MB 使用」は variant のバイト数の合算。

**「利用可能量は取得できません」は別経路ではなく、起動直後の一過性の表示だった。** 実測：描画直後は「取得できません」、1.5秒後は「1,115MB」。同じ `refreshUsage` が非同期で返る前を見ていた。`quotaChecked` を状態に足し、確認中と取得不能を区別した。

**どちらの数字を採るか**：分子はアプリが数えた variant の合計、分母は `estimate().quota`。ご指摘の突き合わせ（書き出し 7,614,731 ≒ 合計 5,670,182 × 4/3 ＋ JSON 分）でアプリ側が正しいことが裏付けられているので、`estimate().usage` は使わない。この比が 80% を超えたら警告を出す（`STORAGE_WARN_RATIO`）。

現在の値：5,670,182 ÷ 1,108,311,253 ＝ **0.5%**。後半で9点を足しても届かない。
