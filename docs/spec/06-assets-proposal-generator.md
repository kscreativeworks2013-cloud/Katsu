# 第5章｜画像アセットとProposal Generator

本章の位置づけ：
提案書の実体の大部分は画像である。テキスト前提でレイアウトエンジンを組むと全面的なやり直しになるため、Proposal Generator の設計に先行して、画像アセットのデータモデルを本章冒頭で確定する。

5-1. 画像アセットのデータモデル

アセットの実体（origin）：
・upload：利用者が持ち込んだファイル（実写・ロゴ・資料画像）。source はファイル名。
・external：外部URL参照。source はURL。実体は保持せず、表示時に参照する。
・ai：AI生成画像。source は生成条件の要約、runId に生成ラインを持つ。

保存先：
・アセットは「メタデータ」と「実体」を分けて扱う。
・メタデータ（id、origin、label、source、runId、mimeType、createdAt）は他の状態と同じく localStorage に保存する。
・実体は本フェーズではブラウザ内に持たない。プレビュー用のサムネイル（data URI）のみを、上限付きで localStorage に持つ。フル解像度の実体保存はサーバー側永続化フェーズで扱う。

provenance の拡張：
・アセットの出自はフィールドの provenance とは別に、アセット自身が origin として持つ。AI生成画像（ai）か持ち込み実写（upload／external）かはこの origin で常に区別できる。
・ai アセットは runId で生成ラインに遡れる。提案書に載る全画像について「どこから来たか」を出力時に表示できることを要件とする（クライアントへの説明責任のため）。

参照解決：
・ムードボードのタイル、ショットリスト（絵コンテのフレーム）、ポートフォリオの作品は、それぞれ任意で assetId を持つ。
・参照は resolveAsset で解決する。アセットが見つからない場合・サムネイルが退避済みの場合は、既存のグラデーションプレースホルダにフォールバックし、参照切れで画面を壊さない。

提案書テンプレートのスロット：
各章は画像スロットを宣言する。スロットは「どこから画像を引くか（source）」と「何枚入るか（capacity）」を持つ。
・表紙：ブランドロゴ（logo、1枚）＋キービジュアル（moodboard、1枚）
・ブランド分析：ブランドイメージ（moodboard、2枚）
・撮影コンセプト：採用案のキービジュアル（moodboard、1枚）
・ムードボード：タイル一覧（moodboard、8枚）
・ショットリスト：絵コンテのフレーム（shots、カット数分）
・実績（ポートフォリオ引用）：選定作品（portfolio、3枚）
テキストのみの章（スケジュール、見積もり、リスク管理）はスロットを持たない。
スロットの解決はテンプレート側で行い、章の本文生成はスロットに関知しない。テンプレート差し替え（ブランドカラー適用等）はスロット定義の差し替えとして実現する。

localStorage の容量制約への退避方針：
・サムネイルは1枚あたり約96KB、合計約2MBを上限とする。上限を超える登録はサムネイルなしで受け付ける（メタデータは常に保持）。
・保存時に容量超過が起きた場合は、全アセットのサムネイルを落として再保存する。それでも失敗した場合はメモリ上のみで継続する（第4章 4-7 と同じ方針）。
・サムネイルの消失は表示のフォールバックで吸収し、参照（assetId）とメタデータは失わない。

5-2. Proposal Generator の構成

・提案書は「章の並び（テンプレート）×章ごとの本文×画像スロット」で構成する。
・本文は日本語・英語を同一の構成データから導出する。言語別に別の構成を持たない。
・章本文は現時点ではワークスペースの生成物から決定的に組み立てる。章単位のAI生成（文章の書き起こし）は実モデル接続フェーズで章フィールドとして provenance 管理に載せる。

5-3. 出力

・Markdown 出力を最初に実装する（実ファイルとしてダウンロード可能にする）。提案書の全章・全文が崩れなく出ることを、他形式に先行して保証する。
・PDF／PowerPoint／Word はサーバー側またはエクスポートサービスで生成する前提とし、本フェーズではファイル名・履歴・確認フローまでを実装する。
・出力時、stale な章がある場合は確認を挟む（第4章 4-4）。出力物には生成日時と、AI生成画像を含む場合はその旨を記載する。
