次の実装順：

1. **原寸アセットの扱い**（仕様：第7章 08-fullsize-assets.md に記載済み。次はこの実装）。理由：埋め込み画像がサムネイル（最大96KB）である限り、現状の PDF は提出物として成立しない。「PDF が出る」ことと「PDF で提出できる」ことは別であり、後者が満たされるまでは実モデルを繋いでも実案件での通し検証にならない。
   ・**書き直し対象**：第6章 6-9 の容量制約（1枚96KB／合計2MB）と、その上に載っている縮小保持ロジック（`src/domain/assets.ts` の decideThumbnail／storageUsage、`src/lib/importImage.ts` の downscaleToFit）は、本項目で保存先ごと置き換える。
   ・**それまでの制約**：原寸対応が入るまで、この容量制約を前提にした新機能を追加しない。追加するほど置き換え時の手戻りが増える。表示・出力に関わる新しい要求は、第7章の実装を待って載せる。
   ・サーバー側永続化の前倒し分は「アセットストアの契約」であり、稼働サーバーではない（判断と理由は第7章 7-4）。
2. **ビジュアル主導の版面設計**。作業範囲は組版の微調整ではなく、画像を主役にした版面の設計。視覚表現の提案書である以上、1カラムの流し込みは提案内容そのものの説得力を損なう。表紙・ムードボード・ショットリストを中心に、画像が支配的な面付けと、テキストがそれに従属するレイアウトを定義する。PDF と PowerPoint の両方に適用し、ブランドカラーのテンプレート差し替えもここに含める。AI生成アセットを表紙全面へ既定で割り当てない規約（第7章 7-3）もここで実装する。
   ・**実モデル接続より先に行う理由**：モックエンジンは決定的なので、同じ内容のまま版面だけを何度も出し直して比較できる。実モデルを先に繋ぐと出力が毎回変わり、版面の良し悪しと生成内容の当たり外れを切り分けられなくなる。版面の評価には固定された入力が要る。
   ・原寸（項目1）が入った直後は、版面を詰める条件が最も揃っている。実寸で置ける画像があって初めて、面付けの判断が現実の解像度に基づく。
   ・**完了時点で実案件を1本通す**。原寸と版面が入れば、モックのままでも提案書として成立する PDF が出るはずである。仕様を積み上げ続ける前に、実際にクライアントへ出せる品質かを一度確かめ、その結果で以降の優先順位を見直す。ここで分かることの例：版面が実案件の情報量に耐えるか、原寸の保存容量が実運用で足りるか、preview 単段（第7章 7-6）で一覧の描画が重くないか、文章の質と体裁のどちらが先にボトルネックになるか。
3. 実モデル接続（GenerationEngine の実装差し替え、設定画面のモデル別名との結線、モデル別の出力解像度の実測と記録（第7章 7-3）、画像生成によるAIアセット登録、失敗時の再試行とレート制御）
4. API設計とサーバー側永続化の全体（localStorage からの移行、認証と権限。1で前倒しした部分を正式な形に収める）
5. Word レンダラ（第6章 6-5 のレンダラを1つ足すだけ。優先度は低い）
