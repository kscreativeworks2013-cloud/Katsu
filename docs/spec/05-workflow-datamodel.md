# 第4章｜AIワークフロー＋データモデル

フェーズ統合の理由：
ステップの入出力契約と再生成時の競合解決は、フィールド単位の provenance（生成の出自）を持つデータモデルなしには定義できない。「どのフィールドが AI 生成で、どれが手動編集済みで、どれが未生成か」「どの生成ラインで書かれたか」「いつ更新されたか」が判定できなければ、上書き可否も差分提示も決められない。したがって本章は AIワークフロー設計とデータモデル設計を同一フェーズとして扱う。

4-1. データモデル：provenance
全ての生成結果は、値そのものとは別に、フィールド単位のメタデータを持つ。

フィールドメタデータ：
・origin：generated（AI生成）／edited（手動編集済み）／empty（未生成）
・runId：そのフィールドを書いた生成ラインのID。手動編集の場合は編集直前の runId を保持する。
・updatedAt：最終更新時刻（ISO 8601）

生成ライン（Run）：
・id：生成ラインID
・stepId：対象ステップ
・startedAt／finishedAt
・status：running／applied／discarded／failed
・inputsHash：生成に使った入力の要約。上流変更の検知に使う。
・engine：使用したエンジン識別子（実モデル／テストダブル）

ステップ記録（StepRecord）：
・status：todo／running／review（確認待ち：Run が完了し、差分プレビューが未適用の状態）／done
　review は「適用するまで書き込まない」という本章の中核状態を表す独立した語彙であり、生成中（running）とは区別する。
・lastRunId：適用済みの最新 Run
・stale：上流の再生成により、内容が最新の前提と一致しなくなった状態
・staleSince：stale になった時刻
・staleCause：stale の原因となった上流ステップID

粒度：
provenance はフィールド単位で持つ。コレクション（競合一覧、コンセプト一覧、ムードボードのタイル、ショットリスト）は**コレクション全体で1フィールド**として扱う。アイテム単位の3方向マージ（生成前・生成後・手動編集の突き合わせ）は本フェーズのスコープ外とし、次フェーズで検討する。コレクション内の1件でも手動編集された場合、そのコレクションは edited として保護される。差分プレビューでは、コレクション行に「中身を確認」の展開を設け、現在とアイテム一覧・生成結果とアイテム一覧を突き合わせて見られるようにする（件数表示だけで上書き可否を判断させない）。

4-2. ステップ入出力契約
各ステップは以下を宣言する。

・id：ステップ識別子
・dependsOn：直接の上流ステップID（複数可）
・inputs：生成に使う入力の抽出関数。案件情報と上流ステップの出力のみを参照し、下流には依存しない。
・outputFields：このステップが書き込みうるフィールドパスの列挙。
・inputsHash：inputs から決定的に算出する要約値。

契約上の制約：
・ステップは outputFields に列挙されたフィールド以外を書き換えてはならない。
・ステップは dependsOn に無いステップの出力を読んではならない。
・同一の inputs から同一の出力が得られること（テストダブルでは厳密に、実モデルでは近似的に）。

4-3. runStep の正式仕様
「既存があれば上書きしない」は廃止する。

実行手順：

1. 実行要求（requestRun）：対象ステップの inputs を確定し、Run を作成して status=running とする。
2. 生成：エンジンが outputFields に対する提案値を返す。
3. 差分の算出：フィールドごとに、現在値・提案値・origin を突き合わせ、次の3分類にする。
   　・上書き（origin が generated または empty で、提案値が現在値と異なる）
   　・保護（origin が edited）＝ 既定では適用しない
   　・変更なし（提案値が現在値と一致）
4. 差分プレビューの提示：既定では「上書き」と「保護」のみを表示し、「変更なし」は件数付きの折りたたみとする（判断対象だけを見せる）。既定の適用選択は「上書き」のみ。保護されたフィールドは明示的に選択した場合のみ、変更なしは適用しても意味を持たないため選択対象にしない。上書きも保護も無い場合は「生成結果は現在の内容と一致」と表示し、閉じるのみとする。
5. 適用（applyRun）：選択されたフィールドのみを書き込み、書き込んだフィールドの origin を generated、runId を当該 Run のID、updatedAt を現在時刻に更新する。Run は applied になる。
6. 破棄（discardRun）：何も書き込まず Run を discarded にする。ステップの状態は実行前に戻す。

補足：
・変更なしのフィールドは適用対象に含めない。値も provenance も更新しない。
・outputFields を持たないステップ（提案書プレビュー、出力）は差分が生じないため、プレビューを挟まずそのまま完了にする。
・生成が失敗した場合は Run を failed とし、ステップの状態は実行前に戻す。既存データは一切変更しない。
・手動編集は即時に origin=edited、updatedAt を更新する。以降その値は再生成から保護される。

Run の並走：
・同一ステップに対する Run は同時に1本まで。実行中・確認待ち・失敗表示中のステップは、解決（適用・破棄・閉じる）まで再実行できない。
・異なるステップの Run は並走を許容する（stale 一覧から複数の再生成を続けて起動できるため）。
・差分プレビューは「開いているステップのもの」だけを表示する。他ステップの確認待ちはステッパーに review として示し、そのステップへ移動するとプレビューが表示される。

4-4. カスケード無効化
上流ステップを再生成したとき、下流ステップをどう扱うかを定義する。

選択肢A：自動再生成
・利点：常に整合が取れる。利用者の操作が少ない。
・欠点：手動編集の破棄が連鎖する。AI呼び出しのコストと待ち時間が上流1回の操作で下流全体に波及する。利用者が意図しない変更が広範囲に発生する。

選択肢B：staleマーク＋手動判断
・利点：手動編集を保護できる。コストと待ち時間が予測可能。どこが古いかが可視化される。
・欠点：stale のまま提案書を出力しうる。ステップ数が増えるほど再生成の判断が利用者の負担になる。

選択肢C：下流ロック
・利点：不整合の混入を構造的に防げる。
・欠点：上流の軽微な修正でも下流の作業が止まる。実務では上流（ブランド分析やコンセプト）を撮影直前まで微修正するため、停止コストが高い。

決定：**選択肢B を採用する。**
提案書は人が最終責任を持つ制作物であり、AIの再生成でその判断を上書きしてはならない。Bの欠点は次の2点で補う。
・出力の直前で警告する：提案書プレビューと出力画面に stale 章の一覧を表示し、出力実行時に確認を挟む。ただし出力自体はブロックしない（古いままでも出したい場面が実務にあるため）。
・再生成の導線をまとめて出す：案件内のどの画面にいても、stale なステップの一覧と、その場から再生成を起動する操作を表示する。ただし各再生成は 4-3 の差分プレビューを個別に通す。1操作で下流をまとめて確定させる導線は用意しない（それは選択肢Aと同じ問題を持ち込むため）。

stale の判定：
・あるステップの Run が applied になり、かつ**値が実際に変化したフィールドが1つ以上ある**とき、その下流（推移的に到達可能な全ステップ）のうち status=done のものを stale にする。値が変わらなかった再生成では下流を stale にしない。
・手動編集も同様に扱う。あるフィールドが編集されたとき、そのフィールドを出力するステップの下流のうち status=done のものを stale にする。生成か手動かにかかわらず、上流の値が変われば下流の前提は変わるため。
・コンセプトの採用案の変更も、ムードボード以降の入力を変えるため stale を伝播させる。
・stale はステップの再生成が applied になった時点で解除する。
・確認済み：利用者は stale なステップを「確認したが再生成不要」として確認済みにできる。確認済みは stale 表示を解除し、その判断（時刻と原因ステップ）をステップ記録に保持する。その後に上流が再び変化した場合は確認済みを破棄し、改めて stale に戻す。これが無いと選択肢Bは警告の常時点灯に劣化し、出力直前の警告が機能しなくなる。
・stale は「古い可能性がある」という表示であって、データを無効化するものではない。stale なステップの内容は引き続き閲覧・編集・出力できる。

4-5. ストリーミング
決定：**本フェーズでは非ストリーミングとする。現行のスケルトン表示を維持する。**

理由：
・生成物はフィールド単位の構造化データであり、部分適用は 4-3 の差分プレビューと両立しない。トークン単位で画面へ流し込むと、利用者は「まだ適用されていない提案値」を確定値と誤認する。
・現行の生成は1ステップあたり数フィールドで、体感待ち時間はスケルトンで十分吸収できる。

将来ストリーミングを採用する場合の再設計見積もり：
・価値があるのは長文を返す画面に限られる。対象は提案書プレビュー（章単位の本文生成）、AIプロンプト生成（プロンプト本文）、ブランド分析（記述項目）の3画面。
・必要な変更：エンジンインターフェースへの進捗コールバック追加、差分プレビューへの「ストリーミング中は提案パネル内にのみ描画し、確定は適用時」という表示規則の追加、中断操作の追加。
・見積もり：エンジン層1〜2日、差分プレビューの表示規則1日、対象3画面の再設計2〜3日。合計4〜6日規模。
・現時点の準備：エンジンインターフェースに任意の進捗コールバックを受け取れる余地だけ残し、実装はしない。

4-6. エンジンとテストダブル
生成処理はインターフェースの背後に置く。

・GenerationEngine：Run 要求を受け取り、outputFields に対する提案値を返す。実モデル呼び出しと、テストダブルは同一のインターフェースを実装する。
・テストダブル（現行の generate.ts を利用するモックエンジン）は**削除せず恒久的に残す**。案件の入力値から決定的に組み立てるため、Vitest の実行結果が入力に対して常に一定になる。
・実モデル接続後も、単体・コンポーネントテストとCIはテストダブルを使う。実モデルを使う検証は別系統（手動またはE2Eの別スイート）で行う。
・アプリはエンジンを注入で受け取り、既定はテストダブルとする。

4-7. 永続化
本フェーズに含める。競合解決の検証には、リロードをまたいで手動編集と provenance が残る必要があるため。

・保存先：localStorage。単一キーに、案件・生成物・provenance・Run履歴・ポートフォリオ・設定をまとめて保存する。
・スキーマバージョンを持ち、読み込み時にバージョンが一致しない場合はシードデータで初期化する（本フェーズでは移行処理を書かない）。
・保存が失敗した場合（容量超過・プライベートモード等）はアプリを止めず、メモリ上の状態のみで動作を継続する。
・サーバー側の永続化とマルチユーザーの同時編集はスコープ外。

4-8. UI制約の解除
8ステップ・13画面は**暫定であり、確定仕様ではない**。

・ワークフロー設計はステップ数・順序・依存関係の変更を許容する。ステップの分割・統合・追加が必要と判断された場合、それを優先し、UIが設計に追従する。
・ステッパー、サイドバー、進捗率、パンくずはステップ定義から生成しており、ステップ定義を変更すれば画面は自動的に追従する。ステップの増減で画面改修が必要になるのは、8件を超えたときのステッパーの折り返し表示のみ。
・第3章の画面別記述（3-4〜3-11）は、対応するステップが変更された場合に読み替える。第3章の全体方針・共通レイアウト・状態設計・アクセシビリティ・レスポンシブは、ステップ構成が変わっても維持する。
